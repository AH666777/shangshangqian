## 三、缺陷清单

> 严重级别定义：**P0** = 上线前必须修复（安全/数据损坏）；**P1** = 影响功能正确性；**P2** = 质量与可维护性；**P3** = 整洁度。

### P0-1 云函数信任客户端 `openid`，存在越权（IDOR）

- **位置**：`yqsss-uniapp/uniCloud-alipay/cloudfunctions/yqsss-auth/index.js:174-285`
- **问题**：`getProfile` / `updateStats` / `saveRecord` / `unlockAchievement` / `getAchievements` 五个 action 全部直接读取 `event.openid`，**没有任何身份校验**，也不校验该 openid 是否属于当前调用者。
- **影响**：任何拿到他人 openid 的请求方，可读取其档案、覆盖其统计、以其名义写入记录、代其解锁成就。这是典型的水平越权。
- **修复建议**：
  1. `wxLogin` 成功后签发会话票据：`token = HMAC_SHA256(openid + exp, SERVER_SECRET)`，返回 `{ openid, token, exp }`；
  2. 其余 action 一律改为从 `event.token` 解析 openid，校验签名与过期时间，**禁止**再从 `event.openid` 取值；
  3. `SERVER_SECRET` 走云函数环境变量，与 `WX_APPSECRET` 分开。

### P0-2 `points` 由客户端覆盖，经济系统可伪造

- **位置**：`index.js:196` → `if (typeof stats.points === 'number') patch.points = stats.points;`
- **影响**：前端可任意写入积分/抽签数，服务端无任何来源校验。若未来接支付或兑换，直接资损。
- **修复建议**：`points` 移出 `updateStats` 白名单，改由服务端按 `saveRecord` 事件累计；若必须回传，改为"增量 + 服务端上限校验"。

### P0-3 `users.openid` 无唯一索引 + 先查后插的竞态

- **位置**：`users.index.json`（`MgoIsUnique: false`）、`index.js:108-135`
- **影响**：并发首登（如快速重试、双端同时登录）会插入多条同 openid 用户，后续 `where({openid}).limit(1)` 命中不确定，统计与成就被拆散到多条记录。
- **修复建议**：把 `idx_openid` 改为唯一索引；`upsertUserByOpenid` 改用 `add` 捕获重复键后回查，或用事务。

### P1-4 H5 `updateNickname` 不更新用户索引 → 身份分裂（已实测复现）

- **位置**：`yqsss/js/auth.js:121-127`
- **证据**（沙箱实测）：
  ```
  登录"张三" → 改名"李四" → 退出 → 登录"张三"：isNew=false，昵称回到"张三"（旧档案）
                                    → 登录"李四"：isNew=true（同一人被当成新用户）
  ```
- **根因**：`_user.nickname` 改了，但 `yqsss_users` 仍以旧昵称为 key 存档，未迁移。
- **对比**：uni-app 版 `modules/auth.js` 已按 `id` 主键并调用 `_saveUser` 回写，**H5 版落后于 uni 版**。
- **修复建议**：H5 版照抄 uni 版策略——档案表改以 `id` 为 key，改名后 `_saveUser(this._user)`。

### P1-5 `buildProfileHistoryHtml` 未转义日期标签（已实测注入成功）

- **位置**：`yqsss/js/ui/view-model.js:106` → `<span ...>${dateLabel}</span>`
- **证据**：传入分组键 `<img src=x onerror=alert(1)>`，输出 HTML 原样保留该标签（`true`）。
- **影响**：`dateLabel` 来自 `createdAt.split('T')[0]`，而 `createdAt` 读自 localStorage，可被同域脚本或调试工具篡改。同文件其余字段均已 `escapeHtml`，此处属遗漏。
- **修复建议**：`${RulesCore.escapeHtml(dateLabel)}`；同时补一条回归用例。

### P1-6 深度解签成就埋点前置到抽签时，成就贬值

- **位置**：`yqsss-uniapp/src/modules/lottery.js:73-75`（`if (!ADS_ENABLED) Storage.countFeatureEvent('deepAnalysis')`）
- **影响**：`ADS_ENABLED = false` 时每次抽签都计一次"使用深度解签"，导致 `first_deep`（首签即得）、`deep_10`（十签即得）**与用户是否真看深度解签无关**。
- **连带**：`smoke/achievement-flow.test.mjs` 中 2 条断言因此失败（见第五节）。
- **修复建议**：改为在 `result.vue` 深度解签板块实际渲染时计数（`onShow` + `deepUnlocked` 判定，同一签文去重），删除 `draw()` 中的计数。

### P1-7 `doShake` 异常时 `isDrawing` 永久锁死

- **位置**：`yqsss/js/app.js:265`、`284`
- **问题**：`await Lottery.draw()` 未包 `try/finally`，`Lottery.isDrawing = false` 在成功路径末尾才执行。任一步抛错（存储写入失败、配额异常等），`isDrawing` 永远为 `true` → 摇签按钮彻底失效，只能刷新页面。
- **修复建议**：`try { ... } finally { Lottery.isDrawing = false; }`。

### P2-8 `poster_5` 口径与测试不一致，smoke 永久红灯

- **位置**：`src/core/achievements.js:256-258`（实现取 `sum.shareCount`）；`smoke/achievements.test.mjs:183`（断言按 `posterCount` 供给）
- **判定**：**实现侧是对的**（"累计分享 5 次" → `shareCount`），测试夹具漏了 `events.share`；但 `poster_1` 用 `posterCount`、`poster_5` 用 `shareCount`，命名几乎相同而口径不同，极易再次误改。
- **修复建议**：修正测试夹具；同时把两个成就 id 改为 `poster_1` / `share_5`，或在注释中显式写明两者口径差异。

### P2-9 成就解锁监听器只增不减（内存泄漏）

- **位置**：`src/modules/achievement.js:142-144`（仅 `onUnlock`，无 `offUnlock`）；调用点 `src/pages/result/result.vue:110`（每次 `onLoad` 注册）
- **影响**：每次跳转解签页都往模块级数组塞一个闭包，持有已销毁的页面实例；抽签次数越多，内存与回调开销越大，且会向废弃页面推送状态。
- **修复建议**：提供 `offUnlock(fn)` 并在 `onUnload` 注销；或改用一次性订阅 `onceUnlock`。

### P2-10 `shake.vue` 抽签定时器未清理

- **位置**：`src/pages/shake/shake.vue:146`
- **影响**：900ms 动画期间用户返回上一页，定时器仍会执行 `Lottery.draw()` 并 `redirectTo`，出现"未操作却消耗次数"或路由异常。
- **修复建议**：保存 timer id，`onUnload` 中 `clearTimeout`。

### P2-11 云端无任何限流 / 防刷

- **位置**：`index.js` 全文件
- **影响**：`saveRecord` 可被无限调用（存储成本 + 数据污染）；`wxLogin` 无频率限制；`unlockAchievement` 单次最多 49 条但可高频重放。
- **修复建议**：按 openid 做分钟级计数（可存 `users` 或独立 `rate_limit` 集合），超限返回 429 语义错误码。

### P2-12 云端统计整包覆盖，多设备互相踩踏

- **位置**：`src/modules/auth.js:129-153` + `index.js:186-208`
- **影响**：`syncStatsToCloud` 把本地全量 stats 直接覆盖云端，`updateStats` 注释也写明"以客户端统计为准"。两台设备交替使用会互相回退进度。
- **修复建议**：改为字段级 max 合并（`totalDraws` 取大、`lastDrawDate` 取新），或引入 `updatedAt` 做乐观锁。

### P2-13 双端 core 层整份复制，已开始漂移

- **数据**：`core` 层 H5 1,550 行 / uni 1,546 行，`diff` 差异仅出口语句；门面层 `auth.js` 194 行 vs 366 行。
- **已发生的漂移**：`normalizeLevel`（"下吉签"→"蓄力签"）仅 uni 有；`updateNickname` 修复仅 uni 有。

## 四、代码质量评估

### 做得好的地方

1. **分层纪律严格**：`core/` 不引用 `document/window/localStorage/wx/uni`，且有测试（`classic-script.test.js:81`）自动守护这条约束——这是很少见的自我约束。
2. **依赖注入到位**：`RulesCore.weightedRandom(items, probKey, rng)` 允许注入随机源，抽签逻辑可确定性测试。
3. **存储可插拔**：`StorageAdapter` 抽象出字符串/JSON 两级接口，H5 与小程序共用同一套业务代码。
4. **时钟口径统一**：全部使用本地时间字符串（`localISO`）而非 `toISOString()`，规避了 UTC+8 偏移；云函数侧用 `bjDateKey` 统一到 UTC+8。
5. **注释解释"为什么"而非"做什么"**：大量决策记录（合规改写、排行榜口径、500 条上限的影响）显著降低后续维护成本。

### 需要改进的地方

1. **双端复制**：约 2,100 行重复，已出现行为漂移（见 P2-13）。这是当前最大的长期维护成本。
2. **无静态检查**：无 ESLint / Prettier / TypeScript，`any` 型隐式契约全靠注释。建议至少接入 ESLint（`no-unused-vars`、`no-undef`、`no-floating-promises`）。
3. **防御式编程不均衡**：`rules.js` 全函数对 `null/undefined` 友好，但 `app.js`、`auth.js` 存在 `nickname.trim()` 这类未判空调用（`updateNickname` 若传 `undefined` 直接抛 TypeError）。
4. **错误处理策略粗糙**：全局 `unhandledrejection` 一律弹"操作未能完成"，会掩盖真实缺陷（P1-7 就是被这层吞掉的）。

### 5.4 测试设计评价

**优点**

- `build.test.js` 把"改 class 后必须重新编译 Tailwind"变成自动化断言，防止样式静默失效——这是本项目最亮眼的一条测试。
- `classic-script.test.js` 校验"js/ 下不得出现 ESM 语法"、"core 层不得引用平台 API"、"装载顺序依赖先行"，把架构约束固化成了回归防护。
- `smoke.test.js` 用 `node:vm` 真实解析 `index.html` 的 `<script src>` 顺序装载，等价于浏览器语义，比 mock 更有说服力。

**问题**

1. **测试未纳入流水线**：`yqsss-uniapp` 的 `package.json` 没有 `test` 脚本，两个 smoke 只能手动 `node` 跑；根目录无 CI。红灯因此可以长期存在。
2. **安全边界零测试**：云函数 6 个 action 无一条用例，"客户端可传任意 openid"这种问题在任何测试下都会暴露，但一条都没有。
3. **缺少契约测试**：前端与云函数的字段名（`totalDraws` / `dateKey` / `unlockedAt`）靠人工对齐，无 schema 校验。
4. **断言风格偏"能跑通"**：smoke 多为流程连通性，缺少异常路径（网络失败、并发抽签、存储写满）。
